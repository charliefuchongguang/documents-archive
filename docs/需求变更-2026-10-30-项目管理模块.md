## 0. TL;DR

1. **三次纠偏**：把合同当项目锚点（结构错）→ 把合同当业务主数据（定位错）→ **把业主的立项工程当成了系统主对象（主次错）**。
2. **系统主对象是归档项目**：一份服务合同对应一个归档项目，归档和查询都围绕它。侧栏一级入口就是「归档项目」，原「全部项目 / 招标 / 咨询 / 造价」四个并列入口收成页内分类切换。
3. **工程项目是业主的立项工程，不是本公司的业务对象**：它只承担"把归档项目分个组"的职责，入口退到「管理」分组下，不做门户、不做主查询路径。
4. **归档流程里就地选/建工程项目**：新建归档时可搜索已有工程项目，无匹配就在同一个表单里展开新建（名称 + 建设单位 + 编号），不跳页、不丢已填内容；也允许暂不归属。
5. **合同模块独立**：`公司贴花合同 2012.xlsx` 是管理员按贴花/缴税需求自建的台账，业务管理不适用。合同模块从业务链路中整体摘出，成为**管理员专属的独立台账**。
6. **不建任何合同—归档项目/工程项目关联**。归档详情不展示合同，统计不含合同额。
7. **历史数据不处理**：1037 条合同原样保留在台账里，不做归属、不做迁移、不做清洗；3 条测试归档项目保留为回归样本。
8. 系统架构只服务于**上线后新归档的项目**，不为历史数据背兼容包袱。

## 1. 定位纠偏

### 1.1 三次偏差

| 层次 | 初版理解 | 实际 | 纠正 |
|---|---|---|---|
| 结构层 | 大合同是容器，项目装进合同 | 合同是凭证，不能当容器 | 项目为容器 |
| 定位层 | 合同是业务主数据，要双向关联、要驱动归档 | 合同是**管理员自用的印花税台账**，与业务归档无关 | 合同独立成台账，业务侧完全解耦 |
| **主次层** | 业主的立项工程是系统的核心对象，一切从"项目"进入 | 业主工程只是**分组维度**；业务人员每天打交道的、要归档要查询的是**本公司承接的那一个个服务** | 归档项目回到主位，工程项目降为管理项 |

前两次纠偏解决的是"合同该不该在业务链里"，第三次解决的是"谁是主角"。**把业主工程当门户，等于让用户每次先选一个跟自己工作无关的东西，再找到自己要办的事。**

### 1.2 数据证据

**台账本体**（`公司贴花合同 2012.xlsx` → `contracts` 表）

| 事实 | 值 |

| 年份跨度 | 最早 2009 年（如 2009-04-23 归档） |
| 合同性质 | 100+ 种自由文本：咨询 103、施工/监理 76、施工 66、造价咨询 48、服务 39、勘察设计 27、PPP咨询 26、承继合同 24、入库协议 6 |

## 2. 目标模型

```
主对象 ── 归档项目（projects）
│  本公司承接的一个服务包的归档单元，例：G8517 施工监理招标
│  列表、搜索、归档入口全部以它为中心
│
├─ 服务类型：招标代理 / 造价咨询 / 咨询（project_categories）
├─ 归档档案：招标文件、中标通知书、履约评价…（files / merged_data）
└─ 所属工程项目（master_project_id，可空）────┐
                                              │ N : 1
分组成员 ── 工程项目（master_projects）◄──────┘
  业主的一个立项工程，例：G8517 屏山至兴义国家高速公路
  不是本公司承接的项目，只用于把归档项目归堆
  入口：管理分组，非业务主路径

独立台账（管理员维护，与业务无关联）
合同台账（印花税）：合同名称、对方单位、合同性质、金额、应贴花、已贴花、份数、归档日期
```

**边界规则**

| 规则 | 说明 |
|---|---|
| 归档项目 ↔ 归档档案 | 1 : N，与改造前完全一致，**流程零改动** |
| 工程项目 ↔ 归档项目 | 1 : N，归档项目的 `master_project_id` **可为空** |
| 归档项目是否为系统主对象 | **是**。列表、搜索、归档入口全部以它为中心 |
| 工程项目地位 | 分组维度，不做门户首页、不做默认筛选、不进业务导航 |
| 合同 ↔ 归档项目/工程项目 | **无关联**。不建表、不加字段、不做双向入口 |
| 合同 ↔ 合同 | 保留 `parent_contract_id` 由管理员自行维护（补充协议/付款挂主合同），与业务无关 |
| 合同可见性 | 仅管理员。普通账号在导航、接口、导出中均不可见 |

> 为什么不保留"弱关联"：只要字段存在，就一定会有人问"为什么不自动带出来""为什么统计对不上"。既然业务不需要，就不留钩子。

> 为什么工程项目必须存在而不是直接删掉：同一工程的多个服务包在业务上确实需要一起看（"这个高速我们做了几个咨询"），需求真实但低频，适合降级为分组而不是删除。

## 3. 概念与命名

这一版把两层对象的 UI 名称调了顺序。**表名一律不动**，只改展示层与接口别名。

| 业务叫法 | UI 名称 | 数据库载体 | 本次处理 |
|---|---|---|---|
| 本公司承接的一个服务包 | **归档项目** | 现有 `projects`（**不改表名**） | 加 `master_project_id`；UI 从"子项目"改回"归档项目" |
| 服务类型 | 服务类型 | 现有 `project_categories`（招标/咨询/造价） | 复用，不新增枚举 |
| 业主的立项工程 | **工程项目** | 新增 `master_projects` | 新增；入口降级到「管理」 |
| 合同 | **合同台账**（副标题：印花税，管理员维护） | 现有 `contracts` | 保留，移除业务耦合 |
| 归档档案 | 归档 | 现有 `files` / `merged_data` | 不动 |

> **表名与 UI 名称反直觉，这是刻意的。** `projects` 是归档项目（主），`master_projects` 是工程项目（辅）——名字里的 master 是"上一级"，不是"更重要"。改表名的代价是 `files`、`merged_data`、两个搜索索引表、全部关联 SQL 全要动，收益只是名字好看。在 `init.js` 的表注释里写清楚即可。

**为什么不叫"子项目"**：系统的主对象不该叫"子"。业务人员口中说的"项目"就是自己承接的那一个服务包，`projects` 表原本也叫项目。v1.3 引入"子项目"是为了给业主工程腾位置，现在主次调回来，"子项目"这个词反而制造了"它比工程项目低一等"的误导。

**导航结构（旧 → 新）**

| 旧 | 新 | 理由 |
|---|---|---|
| 工作台 | 工作台 | 不变 |
| 全部项目 / 招标 / 咨询 / 造价（四个并列） | **归档项目**（一项）+ 页内分类切换 | 这四项本来就是同一个列表的不同过滤，不该占四个导航位 |
| 归档（独立项） | 并入「归档项目」，通过「进入归档」动作 | "归档"是动作不是对象，作为导航项会和对象混淆 |
| — | **管理 / 工程项目** | 新增，从主路径降级 |
| 管理 / 合同台账 | 管理 / 合同台账 | 不变，仍仅管理员可见 |

## 4. 数据模型变更

### 4.1 新增 `master_projects`（工程项目）

> 表名里的 master 指层级上的上一级，不是"更重要"。业务主对象仍是 `projects`（归档项目）。

```sql
CREATE TABLE master_projects (
  id              TEXT PRIMARY KEY,
  name            TEXT NOT NULL,
  project_no      TEXT DEFAULT '',
  owner_name      TEXT DEFAULT '',
  owner_credit_code TEXT DEFAULT '',
  region          TEXT DEFAULT '',
  industry        TEXT DEFAULT '公路',
  total_investment REAL,
  construction_scale TEXT DEFAULT '',
  manager         TEXT DEFAULT '',
  status          TEXT DEFAULT 'active',
  remark          TEXT DEFAULT '',
  created_by      TEXT,
  created_by_name TEXT DEFAULT '',
  created_at      TEXT DEFAULT (datetime('now')),
  updated_at      TEXT DEFAULT (datetime('now'))
);
CREATE UNIQUE INDEX idx_master_projects_no ON master_projects(project_no) WHERE project_no <> '';
CREATE INDEX idx_master_projects_name ON master_projects(name);
CREATE INDEX idx_master_projects_owner ON master_projects(owner_name);
CREATE INDEX idx_master_projects_status ON master_projects(status);
```

不做 (name, owner) 硬唯一：同名跨年度真实存在，用选择器里的相似提示代替约束。

**编号规则（D7）**

| 场景 | 规则 | 示例 |
|---|---|---|
| 业主有编号 | 原样采用 | `G8517-2025-01` |
| 业主无编号 | `P` + 年份 + 3 位流水 | `P2025-001` |
| 归档项目 | 沿用现有 `ZEC-` 规则不变 | `ZEC-Z26G-003` |

新建 `master_project_no_seq(year, current_seq)`，与归档项目编号序列分开，避免混号。

### 4.2 `projects` 增列（归档项目）

```sql
ALTER TABLE projects ADD COLUMN master_project_id TEXT;
ALTER TABLE projects ADD COLUMN seq_in_project INTEGER;
CREATE INDEX idx_projects_master ON projects(master_project_id);
```

`category_id` 直接承担服务类型，不新增 `service_type`。

**建设单位要冗余存一份。** 归档项目列表需要按建设单位搜索，如果只存在 `master_projects.owner_name` 上，每次列表查询都要 LEFT JOIN 且无法走索引。做法：`projects` 增加 `owner_name_snapshot`，在新建/改归属时从工程项目带过来，允许手工覆盖（归档项目的合同相对方可能与工程业主不同）。

> 这是唯一一处允许"冗余工程字段"的地方，因为它是搜索条件。除此之外不得把工程的其它字段（总投资、地区、规模）同步到归档项目。

### 4.3 `contracts` 调整（只做减法）

| 动作 | 内容 |
|---|---|
| 废弃 `is_anchor` | 保留列不读写，代码移除全部判断；SQLite 不删列以规避风险 |
| 保留 `is_payment` | 台账内部标记，财务贴花用，34 条历史数据不动 |
| 保留 `parent_contract_id` | 管理员自行维护补充协议/付款从属，不做层级校验 |
| **不新增** `contract_role` | 原为替代锚点而设计，业务已解耦，无需引入 |
| **不新建** 关联表 | `contract_project_links` 直接 DROP |

### 4.4 迁移步骤（`scripts/migrate-20261030-projects.js`）

| # | 动作 | 说明 |
|---|---|---|
| 1 | 备份 `archive.db` | 沿用现有 `archive.db.bak-*` 机制 |
| 2 | 建 `master_projects`、`master_project_no_seq` | 幂等 |
| 3 | `projects` 加两列 | 先查 `PRAGMA table_info` |
| 4 | DROP `contract_project_links` | 确认 0 条后执行 |
| 5 | 1037 条合同 | **不改动、不回填、不清洗** |
| 6 | 3 条测试归档项目 | 保持 `master_project_id = NULL`，作为"未归属"回归样本 |

**不做的事**：不迁移台账数据、不做合同归属、不做性质标准化回填（P1-2 只作用于上线后新录入的合同，历史原值保留）。

## 5. 功能需求

### P0 — 归档项目（主对象）

**P0-1 归档项目列表** `#/projects`（默认首页）
- 页内分类切换：全部 / 招标代理 / 造价咨询 / 咨询（替代原三个导航项），每项带计数
- 列：归档项目名称（副行放标段数等）、编号、服务类型、**所属工程项目（弱色列）**、归档状态、负责人、更新时间、操作
- 筛选：归档状态、年份、负责人、**所属工程项目（排在最后、加宽）**
- 搜索：归档项目名称、编号、建设单位
- 排序：更新时间倒序；**默认不预置状态筛选**（预置"进行中"会让用户以为历史数据丢了）
- 操作：进入归档 / 归入工程（未归属时）
- 顶部提示：`有 N 个归档项目未归属工程项目，不计入任何工程汇总` + 「去归属」

> 「所属工程项目」在列表里用次级灰色、常规字重。它是索引不是主视觉，不与归档项目抢焦点。

> 登录后的默认落地页是这里，不是工作台。工作台保留为概览入口，但它不再是"进门第一屏"。

**P0-2 新建归档（含工程项目选择）** ← 本轮核心
1. **服务类型**：三张可点卡片（招标代理 / 造价咨询 / 咨询），每个带一句说明；不做下拉
2. **归档项目名称**：必填
3. **所属工程项目**：选填，输入即搜
   - 输入停顿 300ms 调 `GET /master-projects/search?q=`
   - 下拉最多 5 条，每条给：工程项目名称、建设单位、**已有归档数**、编号
   - 命中项右侧「选择」
   - 列表底部固定一个「**+ 新建工程项目「{当前关键词}」**」
   - 面板最底部小字「暂不归属」+ 后果说明
4. **就地新建工程项目**：点「+ 新建」后，在输入框下方**内联展开**表单
   - 字段仅三个：工程项目名称（必填）、建设单位（选填）、工程项目编号（选填，留空自动生成）
   - 按钮：「创建并选中」（保存后收起表单、回填输入框）/「返回搜索」
   - **不得跳转页面**，不得清空已填的归档项目名称与服务类型
5. 底部主按钮「创建并开始归档」：保存后直接进入该归档项目的归档流程

> 禁止把"先建工程项目"做成建归档的前置条件。工程项目可空，这是硬规则。

> **工程归属只在"新建/编辑归档项目"这一处出现。** 归档流程内部（上传文件→AI 提取→人工复核→提交→审核→纸质核对）的每个页面都不得插入工程字段或工程选择器。流程中途加字段会打断作业节奏，且那一步用户手里拿的是文件，不是项目档案。

**P0-3 归档项目详情** `#/projects/:id`
- 页头三段：名称 + 编号 / 归档状态事实（类型、状态、负责人、更新） / **所属工程项目 + 「更换」**
- 面包屑：`归档项目 / {工程项目名} / {归档项目名}`，中间一级可点；未归属时两级 + 「未归属」标签
- 归档资料清单：沿用原有字段与流程，**零改动**
- 页头不展示工程的建设单位、总投资

**P0-4 从归档侧补归属**
- 未归属的归档项目，在列表行内提供「归入工程」
- 复用 P0-2 的工程选择器（含就地新建）
- 归属变更权限：见 P0-7

### P0 — 工程项目（管理模块，辅助）

**P0-5 工程项目列表** `#/master-projects`（位于「管理」分组）
- 顶部说明条：`工程项目是业主的立项工程，只用于把归档项目分组，不代表本公司承接的业务`
- 列：工程项目名称（副行：地区/性质/里程）、编号、建设单位、**归属归档（类型计数）**、负责人、操作
- 筛选：建设单位、年份、状态；搜索：名称、建设单位
- 不展示投资额、中标额

**P0-6 工程项目详情** `#/master-projects/:id`
- 页头：工程全量信息（编号、建设单位、地区、总投资、负责人）+ 编辑

## 8. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 业务人员仍想"在归档里看合同" | 需求回潮 | 明确边界：合同是财务台账，业务页不提供 |
| 管理员误以为合同台账还能关联项目 | 使用困惑 | 页面副标题写明"印花税台账 · 管理员维护"；移除所有项目字段入口 |
| **工程项目被当成主入口又被塞满业务字段** | 主次关系再次跑偏 | 工程页不出现中标额、投资进度、合同；只在「管理」分组 |
| **同一工程被重复建** | 分组散乱、汇总失真 | 工程选择器输入即搜，命中列表直接可见；编号唯一约束；管理员可合并（合并列为 P2，不在本期） |
| **归档项目大量不归属** | 工程维度形同虚设 | 列表顶部常驻未归属计数 + 行内「归入工程」；不强制，但可见 |
| 历史 1037 条与新台账混在一起 | 台账统计口径不清 | 台账内按 `source = legacy` 标注"历史导入" |
| 移除关联后旧数据/旧接口残留 | 脏数据、报错 | 迁移脚本 DROP 空表；接口同步下线；前端残留调用一并清理 |

> 关于"归档项目是否需要查重"：**不做**。归档项目编号由系统生成且唯一；同一工程下同一服务类型出现多条同名归档（如分年度、分标段）是真实业务，硬查重会逼用户加后缀。查重职责集中在工程项目侧，由选择器天然承担——输入时就能看到相似工程，不需要独立的 `/similar` 接口和二次确认弹窗。

## 9. 验收标准

1. 默认首页是归档项目列表，侧栏一级入口任一时刻只有一个"项目"概念（归档项目），工程项目不在业务分组。
2. 归档项目列表按服务类型可切换，切换后计数与列表条数一致；「所属工程项目」列显示名称或"未归属"。
3. 新建归档时输入工程关键词能看到匹配列表（含建设单位、已有归档数），无匹配时可就地新建工程项目并自动选中，**全程不跳页、已填的归档名称与类型不丢**。
4. 选择「暂不归属」可正常创建，列表里显示"未归属"，行内可后续「归入工程」。
5. 归档全流程（上传→提取→复核→提交→审核→纸质核对→下载）与改造前一致，无回归。
6. 归档项目详情、工程项目详情、任何导出中**不出现合同信息**。
7. 普通账号导航中无「合同台账」入口；直接访问接口返回 403。
8. 管理员可正常新增/编辑/删除台账记录，付款类筛选可用，`is_anchor` 相关 UI 与接口全部消失。
9. 迁移脚本可重复执行（幂等），执行后 1037 条合同、3 条归档项目数据完整，`contract_project_links` 已删除。
10. 编号：工程项目填业主编号原样保存，留空生成 `P2026-001` 不重号；归档项目沿用 `ZEC-` 规则不变。
11. 普通账号无法删除工程项目（有归属归档时），无法修改他人归档项目的归属。

## 10. 决策定稿（2026-10-30）

| # | 问题 | 结论 | 落地影响 |
|---|---|---|---|
| D1 | 工程项目粒度 | **一个立项一个工程**，跨年度/跨标段不拆 | 去重按立项判断 |
| D2 | `projects` 表演进 | **不改表名**，只加 `master_project_id` | 迁移成本最低 |
| D3 | 合同与归档项目基数 | ~~多对多~~ → **作废**：不再建立任何关联 | 不建 `contract_links` |
| D4 | 归档项目能否无合同 | **允许**（已无合同概念耦合） | 无校验 |
| D5 | `is_anchor` | **彻底废弃** | 移除校验、筛选、UI |
| D6 | 历史数据 | **不补、不处理**，只服务上线后新项目 | 1037 条合同仅作台账 |
| D7 | 编号规则 | 工程项目：业主编号优先，缺失 `P`+年+3位流水；归档项目沿用 `ZEC-` | 新增 `master_project_no_seq` |
| D8 | 谁能新建 | **任何人** | 归档项目与工程项目均可由任意登录用户新建 |
| D9 | 合同模块归属 | **独立台账，仅管理员查看/编辑** | 合同菜单按角色隐藏；移除全部项目关联 |
| **D10** | **谁是系统主对象** | **归档项目**。归档与查询都以它为中心，工程项目只作分组 | 导航重排；工程项目入「管理」 |
| **D11** | **工程项目在哪建** | **归档流程内可建可选**，也可在管理页单独建；不设前置条件 | 内联新建表单，不跳页 |
| **D12** | **两层对象的 UI 命名** | `projects` = **归档项目**（主）；`master_projects` = **工程项目**（辅） | 仅改文案，表名不动 |

### 10.1 实现时必须守住的六条

1. **无关联**：任何地方不得用"建设单位 LIKE""名称 LIKE"把合同和归档项目、工程项目关联起来。
2. **无统计**：业务页、导出、看板都不含合同金额/数量。
3. **无入口**：归档页不放合同入口；合同页不放项目入口。
4. **不强制**：工程项目可空；「暂不归属」必须可用，且不得反复弹窗劝阻。
5. **不跳页**：新建归档时新建工程项目必须内联展开，禁止跳转页面或清空已填内容。
6. **不上移**：工程项目的任何信息（投资额、建设单位作业主信息）不得进入归档项目详情的页头主区。
